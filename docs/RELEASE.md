# Coordinated Git release

`wikibuild/release.py` converts a validated reader candidate into versioned topic
outputs, coordinates exact child commits and writes the immutable umbrella release
manifest. `wikibuild/git_transaction.py` owns Git preparation and recoverable file,
index and branch updates. Neither module creates remotes or deploys Pages.

## Output ownership and storage

Each child records generated ownership in `.wiki-output.json`. The coordinator
owns `site/` and `reference/`; it adopts `README.md` only when it exactly matches
the generator's initial seed. Authored READMEs and other committed files remain
outside generated ownership. Unknown files, including ignored files inside the
generated namespaces, fail validation without being overwritten or staged.

Reviewed authored commits may follow an existing release. After `wiki.py lock`
adopts the clean child commits, allocation verifies that each new HEAD descends
from its prior release commit and preserves that release's exact ownership
receipt and generated bytes. History size includes the authored commits.
Publication and unchanged-release reuse still require the exact selected release
HEAD. Curated definitions use the [authored check contract](CURATED.md).

`wikibuild/ownership.py` owns the receipt format. Small receipts retain schema 1.
Larger receipts use a schema 2 root and hashed `.wiki-ownership/<sha256>.json`
pages, each bounded by the smaller of 64 KiB and the configured file budget.
Directory pages bound the root as the file list grows. Each file record carries
its hash, size and allocation membership; the root checks the complete file map.
The current checkout contains only the metadata pages referenced by its receipt.
Historical receipts remain readable at their pinned Git commits through one
`git cat-file --batch` process per receipt. Ownership metadata is excluded from
Pages output. Unknown or modified metadata pages fail validation and are preserved.

Public site storage retains all releases:

- `data/<hash>.json` stores a selected data pack once across snapshots/releases.
- `objects/<hash>.json` stores immutable snapshot indexes.
- `runtime/<hash>/reader.js` and `.css` preserve each release's reader runtime.
- `releases/<release-id>.json` pins the topic's indexes, runtime and route map.
- `reader.json` selects the latest prepared release. Stable HTML routes load a
  small bootstrap that honors an explicit `release` parameter before loading data.

Generated Markdown remains directly readable in Git. Old release configurations
and packs are retained when the current reference changes. A missing requested
release fails explicitly; the reader never silently substitutes current facts.
Configured URLs are intended deployment destinations until publishing verifies
them. Local Git completion is not evidence of public availability or gameplay
verification.

## Transaction and recovery

The caller holds the umbrella's OS writer lock. Before preparing any child,
validate every destination identity, clean checkout, owned file hash and checkout
lock. Prepare each new tree with an alternate Git index and create its exact
commit object without modifying the checkout. Existing authored files remain in
the base tree; only the declared generated paths are added.

Before checkout mutation, save `.local/rs/<attempt>/plan.json` and a hash-pinned
`.local/releases/pending.json`. The plan records original and target commits,
branch names, trees, file hashes and staged bytes. Topics commit before the hub.
The next invocation finishes a pending transaction before preparing newer work.

Obsolete ownership metadata pages are recorded as deletions with their old hashes.
Promotion removes only those exact bytes; retry accepts an already completed
deletion and rejects an outside edit. The same prepared Git commit includes the
new receipt, new pages and obsolete-page removals. Historical site files are not
deleted by this metadata transition.

Recovery accepts only recorded old/new file content and index trees. Unexpected
branch changes, staged edits or file changes are preserved and rejected. After
file promotion, an index-only two-tree merge preserves Git's staged-change conflict
checks. A compare-and-swap ref update accepts only the recorded previous commit.
See [Git read-tree](https://git-scm.com/docs/git-read-tree) and
[Git update-ref](https://git-scm.com/docs/git-update-ref) for those primitives.

After every child validates, persist `releases/<release-id>.json`, update the
checkout lock and finally advance `releases/latest.json`. The manifest pins child
commits, trees, output hashes, routes, reader inputs and the precise validation
scope. Before that boundary, the previous coordinated release remains selected.
Partial child commits can survive an interruption; retry recognizes and reuses
their exact identities. Publication has a [separate pointer and recovery contract](PUBLICATION.md).

The [capacity contract](CAPACITY.md) owns physical partition allocation, staging,
registry membership and prepared-size checks. Storage partitions install and commit
before dependent logical topics. The release manifest and checkout lock pin every
physical repository while the public route map retains logical topic ownership.
`release_prepare.py` builds and measures proposals before the coordinator saves a
journal. A full entrypoint rolls according to [CAPACITY.md](CAPACITY.md); its
successor installation and the retiring front's final update share that journal.
The manifest's `entrypoints` map selects active physical fronts, while `routes`
continues to name the original topic URLs.

Operational staging lives under `.local/rs/` for recovery and inspection. After
supported publication work completes, the normal update removes staged payloads
that have independently verified committed copies. Journals and small Git
preparation files remain local. [RETENTION.md](RETENTION.md) owns these checks,
retry behavior and the remaining cache-retention work. Historical public records
are retained. Indivisible control metadata still needs implementation.

## Validation and preview

```powershell
py -3 -m unittest discover -s tests -p test_release.py -v
py -3 wiki.py update --operator-report
py -3 tools/check_release.py
py -3 tools/benchmark_release.py
py -3 tools/serve_release.py
```

The preview binds `127.0.0.1` and serves all physical repositories. HTML installs
a local origin mapping; the reader applies it when resolving requests and links.
Configurations, snapshot indexes and data packs keep their published bytes and
hashes. It is a local browser check, not proof of Pages deployment.

Tests use real Git repositories to check exact commits, no-op reuse, historical
pack reuse, authored content, unknown ignored files, modified journals, staged
edits and interruptions during files, between children and after a ref update.
The pipeline integration test commits all 13 fixture topics while content
exceptions remain in its final report.

The independent checker compares generated bytes to the exact committed Git
blobs, checks candidate conservation after release projection, and follows every
retained release to its runtime, snapshot indexes and packs. It imports no builder
modules. The repeat benchmark checks child commits and generated file hashes and
timestamps around an unchanged integrated update.
